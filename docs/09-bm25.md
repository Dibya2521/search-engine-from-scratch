# BM25

## What it is

A ranking function that scores a document for a query by summing, over the query
terms, a weight for how rare the term is multiplied by a *saturating*,
*length-corrected* measure of how often the term occurs in the document.

```text
score(query, doc) = sum over terms of  idf(term) * (tf * (k1 + 1))
                                       ---------------------------------
                                       tf + k1 * (1 - b + b * dl / avgdl)
```

- `tf` is the term's frequency in the document.
- `dl` is the document's length in terms, `avgdl` the corpus average.
- `k1` controls how quickly term frequency saturates. Default 1.2.
- `b` controls how strongly length is corrected. Default 0.75.

The name is literal: it was the twenty-fifth best match formula tried in the
Okapi project at City University London.

## Why it exists

TF-IDF has two properties that do not match how relevance behaves, and BM25 is a
correction for each.

### Term frequency grows without limit

Under TF-IDF, a document containing a term twenty times scores twenty times one
containing it once. That is not how relevance works. The second occurrence of a
word tells you a great deal; the twentieth tells you almost nothing new.

BM25 divides `tf` by a quantity that itself grows with `tf`, so the value
approaches a ceiling of `k1 + 1`. With `k1 = 1.2` and length correction off:

| Occurrences | TF-IDF contribution | BM25 contribution |
| --- | --- | --- |
| 1 | 1x | 1.00x |
| 2 | 2x | 1.38x |
| 3 | 3x | 1.57x |
| 5 | 5x | 1.77x |
| 10 | 10x | 1.96x |
| 20 | 20x | 2.08x |
| 100 | 100x | 2.17x |

The tenth occurrence is worth about 2 percent more than the ninth. The
hundredth is worth almost nothing. This is what makes BM25 resistant to a
document that simply repeats a word.

### Document length is handled implicitly and imprecisely

TF-IDF handles length by dividing each document vector by its own length, which
is a side effect of using the cosine. That corrects length, but it also couples
the correction to every other term in the document and gives no way to tune it.

BM25 compares each document's length against the corpus average and exposes `b`
as the strength of the correction. `b = 0` disables it entirely, `b = 1` applies
it fully. Being able to turn the correction off is what makes it possible to
measure whether it helps, which is not possible when it is baked into the
geometry.

## How it works internally

### The saturation term

```text
(tf * (k1 + 1)) / (tf + k1 * correction)
```

As `tf` grows, numerator and denominator both grow linearly, so the ratio tends
to `k1 + 1`. Small `k1` saturates sooner. At `k1 = 0` the expression collapses to
`1` for any non-zero `tf`, which turns BM25 into a pure inverse document
frequency scorer that only asks whether the term is present. There is a test
asserting exactly that, because it is the cleanest way to show what `k1` does.

### The length correction

```text
correction = 1 - b + b * dl / avgdl
```

At `b = 0` this is `1` and length does not enter. At `b = 1` it is `dl / avgdl`,
so a document twice the average length has its term frequencies effectively
halved. At the default `b = 0.75` it is three-quarters of the way to full
correction.

Length here is measured **after analysis**, so stopwords removed at index time do
not count towards it. That is the correct measure for this index because it is
the number of terms the document actually contributes.

### The inverse document frequency, and a correction to the classic formula

The original formulation is:

```text
idf(term) = log( (N - df + 0.5) / (df + 0.5) )
```

**This goes negative for any term present in more than half the documents.** A
negative weight means a document is *penalised* for containing a query term, so a
document containing every query term can rank below one containing fewer. That is
not a subtlety; it is a wrong answer.

It is a real problem on this project's own collection, not a theoretical one. Of
the 1,061 terms in the 70-document evaluation corpus, three take a negative
weight under the classic formula. The worst is `document`, present in 47 of 70,
which scores **-0.704**: any document matching it would be pushed down for doing
so.

This implementation adds one inside the logarithm:

```text
idf(term) = log( 1 + (N - df + 0.5) / (df + 0.5) )
```

The added constant keeps the argument above 1 for every possible document
frequency, so the weight is never negative. This is what current production
implementations use, and there is a property test over document frequencies from
1 to 500 asserting the weight never goes below zero.

### Query term frequency is ignored

The full formulation includes a third factor for terms repeated *within the
query*, controlled by a parameter usually called `k3`. It is omitted here because
it only has an effect on queries long enough to repeat a term, and typed queries
are not. Most implementations omit it for the same reason.

## How it is implemented here

`BaseRanker` in `ranking.py` holds everything that does not depend on the scoring
formula: the staleness check, and top-k selection by heap. `Ranker` and
`BM25Ranker` supply only the two parts that differ, which are how a query becomes
weighted terms and how one document scores against them.

That split is what makes the two comparable. Both see the same candidate set from
the same matcher, and the same selection rule, so any difference in results comes
from the formula alone.

Everything BM25 needs was already in the index. Term frequency is the length of a
position list. Document length is the sum of a document's position list lengths,
computed in one pass over the postings exactly as TF-IDF's vector lengths are.
No new storage was required.

```bash
uv run search-engine search sample.index "computer science" --scorer bm25
```

## Whether it is actually better: the measurement

This is the part that matters, and the answer is not the expected one.

The judgement set was written and committed **before** BM25 existed, which the
commit history shows. 70 documents, 55 queries, 200 graded judgements.

```bash
uv run python benchmarks/ranking_quality.py
```

| Metric | TF-IDF | BM25 | Change |
| --- | --- | --- | --- |
| Mean average precision | 0.7485 | 0.7586 | +1.3% |
| Mean nDCG@10 | 0.8660 | 0.8772 | +1.3% |
| Mean reciprocal rank | 0.9788 | 0.9818 | +0.3% |
| Mean precision@5 | 0.5921 | 0.5848 | **-1.2%** |

Per-query, BM25 wins 14, loses 12, and ties 29.

**That difference is not distinguishable from chance.** A sign test over the 26
non-tied queries gives p = 0.845. A paired permutation test over 100,000
resamplings, which also accounts for the size of each difference, gives
p = 0.3275. The conventional threshold for reporting a difference is 0.05, and
neither test comes close to it.

### Why the collection could not decide it

Mean reciprocal rank is 0.979 for TF-IDF. The first result is already relevant
for essentially every query, so there is almost no headroom for a better scorer
to occupy. A test collection that both systems nearly saturate cannot rank them.

The collection is also small. 55 queries is at the bottom of what is needed to
detect a difference of this size, and the effect being measured is about one
percent.

### What was decided, and why

**TF-IDF stays the default. BM25 ships as an option.**

This follows a rule written down before the result was known: if the measurement
does not show BM25 is better, record that and keep TF-IDF, because adopting it
anyway would be an appeal to authority. The measurement did not show it. The
default therefore does not move.

BM25 is kept and selectable because it is not worse, it is measurably better on
the specific defect that motivated it, and the honest conclusion is that this
collection cannot separate them rather than that they are equal.

### What would settle it

A larger and harder collection. That is the real-corpus work, and it is the
reason that item now blocks this one rather than the other way round. Roughly:
several hundred queries, documents long enough for length correction to matter,
and queries whose answer is not simply the document with the matching title.

### What BM25 does measurably fix

The motivating case is a five-document corpus where document 4 is the single word
`computer` repeated five times, containing nothing about science, scored against
the query `computer science`.

| Scorer | Document 4's score | As a fraction of the winner |
| --- | --- | --- |
| TF-IDF | 0.4869 | 72% |
| BM25 | 0.9505 | 52% |

BM25 does not remove it from second place, and it should not: the document
genuinely contains one of the two query terms, many times. What changes is the
margin, and 72 percent to 52 percent is the saturation doing exactly what it was
added to do. There is a test pinning both numbers.

## When BM25 is the right choice

- **Documents vary a lot in length.** This is where `b` earns its place. Over a
  corpus of uniform length there is nothing for it to correct.
- **Terms repeat within documents.** Long-form text, and anywhere keyword
  stuffing is possible.
- **You want tunable ranking.** `k1` and `b` are levers; the cosine is not.

It is worth less when documents are short and uniform, which describes titles,
product names and log lines, and when the collection is small enough that every
reasonable scorer gets the same answer, which is what happened above.

**Tuning `k1` and `b` on the same judgements used to evaluate them would be
overfitting.** Doing that properly needs a held-out split, and with 55 queries
there are not enough to split. The defaults are therefore left at the
conventional values rather than fitted.

## Alternatives

| Approach | Adds | Costs |
| --- | --- | --- |
| **TF-IDF cosine** | simplicity, and a geometric interpretation | unbounded term frequency, length correction not tunable |
| **BM25 (this)** | saturation and explicit length correction | two parameters, and no geometric meaning |
| **BM25F** | per-field weighting, so a title match counts more than a body match | needs per-field postings |
| **Divergence from randomness** | a different probabilistic foundation | more parameters, rarely better in practice |
| **Language models with smoothing** | a generative account of relevance | comparable results, smoothing parameter to choose |
| **Learning to rank** | combines many signals, beats any hand-tuned formula | needs click data, a feature pipeline, and a model |
| **Dense retrieval** | matches paraphrases lexical search misses | needs a trained model, cannot prove an exact match |

BM25 is the floor for a serious ranking function rather than the ceiling. Almost
every production system uses it or a variant as the first-pass scorer, then
reranks the top few hundred results with something more expensive.

## How it connects to everything else

- **TF-IDF ranking** is what it replaces, and both remain in the codebase so the
  comparison stays reproducible rather than historical.
- **The inverted index** already stored everything BM25 needs. Term frequency is
  a position list length and document length is their sum, which is why this was
  a scoring change and not a storage change.
- **Stopword removal** changes document length, since length is counted after
  analysis. Removing more words shortens every document, and because the
  correction is relative to the corpus average, uniform removal largely cancels
  out.
- **Evaluation** is the only reason any of this can be claimed. Without the
  judgement set this document would assert that BM25 is better, and that
  assertion would be wrong on this collection.
- **Significance testing** is what turned a plausible +1.3 percent into an honest
  "cannot tell". The difference between those two conclusions is the entire value
  of measuring properly.
